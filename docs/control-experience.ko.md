## 핵심 가치

Conn의 가치는 사람이 에이전트와 같은 실제 PTY를 보며 에이전트의 활동을 이해하고
효과적으로 관리할 수 있게 하는 UX와 어포던스다.

> 사용자는 내부 권한 구조를 외우지 않고도, 에이전트가 지금 무엇을 할 수 있는지와
> 이번 선택으로 무엇이 달라지는지 이해할 수 있어야 한다.
> 반복되는 요청이 무심코 승인하는 습관을 만들어서는 안 된다.

**일관성은 같은 의미의 요청이 같은 위치·움직임·행동을 갖는 것이다.**
모든 요청을 비슷한 카드와 `허용` 버튼으로 만드는 것은 이 기준을 충족하지 않는다.
연결·참여·제어권·명령 검토는 내부에서 분리하되, 사용자는 이어지는 협업으로 이해해야 한다.

## 사용자와 정한 시각 방향

현재의 어두운 터미널, 에이전트 색상, 테두리 효과, 뱃지와 공간을 여는 모션을 유지한다.
제어권 요청은 **오른쪽 Conn 뱃지에서 시작하는 확장 전환**, 명령 실행 승인은
**현재처럼 아래에서 공간을 열며 나타나는 카드**로 구별한다.

참조: [Motion Primitives — Morphing Dialog](https://motion-primitives.com/docs/morphing-dialog).
2026-09-23에 브라우저에서 예제의 열기·닫기와 설명을 확인했다.
참조하는 것은 작은 트리거와 확장된 내용 사이의 위치·크기·모서리 연결감이다.
뱃지에서 실제 액체 형태나 연결 줄기를 그리는 방향은 채택하지 않는다.
배경 블러·전체 화면 잠금·포커스 이동은 예제에서 그대로 복제할 계약이 아니다.

### 제어권: 뱃지가 요청으로 펼쳐진다

1. 새 요청은 오른쪽 뱃지에 대기 상태를 만든다.
2. 같은 시각 요소가 상단 또는 중앙의 읽기 쉬운 요청 패널로 이어진다.
   별도 팝업이 갑자기 생성되는 느낌이나 장식적인 물방울을 피한다.
3. 에이전트·대상 셸·목적·이번에 맡기는 범위를 보여준다.
   `이 셸의 입력을 맡길까요?`처럼 판단 자체가 제목이 된다.
4. `입력 맡기기 / 거절`은 서로 다른 결과가 분명한 행동이다.
   실제 모드와 정책을 따른다. 모든 셸에서 일반 명령이 자동 실행된다고 약속하지 않는다.
5. 접으면 같은 뱃지로 돌아간다. 접기는 거절·허용이 아니며 미해결 요청은 남는다.
   승인하면 뱃지는 현재 제어 주체를 표시한다. 제어 허용은 명령 승인이 아니다.

새 요청 자동 펼침 여부, 상단과 중앙 중 최종 위치는 움직이는 프로토타입에서 결정한다.
타이핑 중 포커스를 빼앗거나 입력 중인 키를 승인 단축키로 소비해서는 안 된다.
명시적으로 패널에 진입한 뒤의 키보드 이동·닫기·포커스 복귀는 함께 설계한다.

### 명령: 실행 내용을 아래에서 검토한다

- 기존 하단 도크의 공간 확보와 모션을 유지한다.
- 제목은 `명령 실행 승인`, 본문은 무엇이 바뀌는지와 왜 확인이 필요한지를 설명한다.
  명령·대상·허용 범위는 펼치지 않아도 판단할 수 있어야 한다.
- 기본 행동은 `한 번 실행 / 거절`. 더 넓은 허용이 제공된다면 적용 대상·규칙·종료 조건을
  명시한 별도 선택으로 다룬다. `세션 허용`이라는 짧은 문구로 범위를 숨기지 않는다.
- 필요한 경우 `제어권은 이미 허용됨` 같은 짧은 맥락을 보여준다.
  매번 연결부터 반복하게 만드는 단계형 마법사로 만들지 않는다.
- 펼치기는 상세 분석을 보조한다. 위험·대상·범위를 원문 JSON 뒤에 숨기지 않는다.

### 알림: 요청으로 안내한다

- 다른 탭이나 앱 밖의 알림은 `어느 셸에서 어떤 판단이 필요한가`를 알려준다.
  클릭하면 해당 요청으로 이동하며 승인·공유·제어권 부여를 하지 않는다.
- 같은 요청의 알림·뱃지·패널은 하나의 요청 신원을 따른다. 여러 건처럼 강조하지 않는다.
- 연결 허용은 `공유 화면 접근`, 제어권 허용은 `이 셸의 입력`, 명령 승인은 `이번 실행`을
  각각 말해야 한다. 연결 허용은 위쪽 도크에 별도 공간을 확보한다.
- 일반적인 진행·완료 안내는 조용히 전달한다. 지속적인 반짝임이나 반복 확대를 쓰지 않는다.
- 해결·거절·취소·만료를 구별하고 오래된 알림으로 끝난 요청을 되살리지 않는다.

## 구현 전 관찰 기록

이번 검토에서는 별도 상태 디렉터리와 합성 파일을 사용하는 실제 Rust 웹 호스트·MCP·공통 UI를
인앱 브라우저에서 조작했다. 사용자 작업 셸과 실제 파일을 변경하지 않았다.

| 단계 | 확인한 동작 | 평가 |
| --- | --- | --- |
| 1. 기본 셸 | 터미널과 Conn 뱃지 중심의 간결한 화면 | 유지할 기반 |
| 2. 연결 허용 | 공유 화면 접근 설명과 `Allow / Deny` | 제어권 허용과 행동 문구가 같음 |
| 3. 제어 요청·펼치기 | 같은 하단 카드, `Allow`, 원문·JSON 상세 | 범위 차이보다 내부 요청 구조를 강조 |
| 4. 일반 명령 | 허용 뒤 합성 파일 읽기가 자동 실행됨 | 정상 흐름; 모든 환경의 보장 아님 |
| 5. 삭제 검토 | 대상·명령·단일 승인과 세션 허용 표시 | 넓은 허용의 범위가 기본 문구에서 불명확 |
| 6. 다른 탭으로 이동·복귀 | 대기 요청 링크로 정확한 탭에 돌아옴; 승인은 계속 대기 | 유지할 동작 |
| 7. 거절·제어권 회수 | 합성 삭제를 거절하고 제어 센터에서 회수 | 회수 동작은 있으나 별도 패널 안에 있음 |

이 표는 구현 전 상태 관찰이다. 새 모핑 전환의 구현·접근성·macOS 실기 검증을 뜻하지 않는다.
화면 캡처만으로 대비 수치, 스크린리더 동작, 짧은 창·확대·동작 줄이기를 통과했다고 말하지 않는다.

## 구현 전에 고정할 상태 계약

- 승인 사유·대상·허용 범위·가능한 선택은 같은 요청 상태에 속한다.
  늦은 상태 조회 때문에 같은 카드의 버튼이나 사유가 바뀌어서는 안 된다.
- 실제 권한 조건이 달라지면 이유를 표시하고 오래된 선택을 거절한다.
  버튼만 고정해 백엔드의 최신 권한 검사를 생략하지 않는다.
- 명령 위험과 셸 상태 확인 실패를 분리한다. 불확실한 셸 상태를 복구하는 일이
  명령 검토를 없애거나 권한을 확대하는 일이 되어서는 안 된다.
- 제어권 회수는 새 에이전트 입력을 막는 것과 이미 실행 중인 프로세스를 중단하는 것을
  구분해서 설명한다. 제어권 회수만으로 모든 작업이 종료된다고 표현하지 않는다.
- 모핑의 시각적 크기 변화와 실제 PTY 크기를 분리한다. 하단 도크는 최종 크기에 맞춰
  공간을 확보하고, 애니메이션 프레임마다 PTY를 리사이즈하지 않는다.

## 다음 검증

정지 이미지 추가보다 **뱃지 → 제어권 요청 → 뱃지 → 하단 명령 검토**의 실제 전환을 먼저 비교한다.
같은 공통 컴포넌트·룬·Rust 경계를 사용하며 별도 하네스 전용 승인 UX를 만들지 않는다.
검증은 반복 요청, 동시 요청, 다른 탭, 취소·만료, 재연결, 느린 상태 응답, 키보드·동작 줄이기,
긴 명령·짧은 창과 실제 macOS 셸까지 포함한다. 각 승인에서 사용자에게
`지금 무엇을 허용했고, 다음에는 무엇을 다시 물을 수 있는가`를 설명하게 해 이해도를 확인한다.
